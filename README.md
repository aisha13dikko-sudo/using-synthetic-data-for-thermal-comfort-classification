# Using Synthetic Data for Thermal Comfort Classification

UCL MSc AI for Sustainable Development project investigating whether **synthetic tabular/time-series data** can stand in for real sensor data when training thermal comfort classifiers — and where that substitution breaks down.

The project works with the [AutoTherm indoor dataset](https://huggingface.co/datasets/kopetri/AutoTherm) (physiological + environmental sensor readings labelled on a 7-point thermal comfort scale), generates synthetic versions of it with several different methods, and compares classifiers trained on real vs. synthetic data — including cold-conditions failure analysis and LLM-based classification.

Supporting folders:

- **`results/`** — CSV outputs and JSON **provenance manifests** (`wk*_manifest.json`) recording the exact run configuration (library versions, random seeds, train/test participant splits, label distributions) for each experiment, so results are traceable back to the notebook cell that produced them.
- **`trajectory_analysis/`** — plots of cold-discomfort sensor trajectories.
- **`llm_generation/`** — synthetic rows generated by an LLM, plus generation logs.
- **`llm_experiments/`** — zero-shot / few-shot LLM classification results (3-class and 7-class).

## Data

The [AutoTherm indoor dataset](https://huggingface.co/datasets/kopetri/AutoTherm) is streamed from the Hugging Face Hub at runtime via the `datasets` library (`load_dataset("kopetri/AutoTherm", "indoor")`) — no raw data is checked into this repository.

## Setup

The notebooks were developed and run in **Google Colab** (Python 3.12, CUDA runtime for the GPU-based generators). Each notebook installs its own extra dependencies in its first cell via `!pip install`, so notebooks can be opened directly in Colab without any local setup — click the "Open in Colab" badge at the top of a notebook.

To run any of the notebooks locally (e.g. in Jupyter) instead:

```bash
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Notes:

- The `wk9`, `wk14`, `wk15`, and `temporal_llm_classification_clean` notebooks call the **OpenAI API** and expect an `OPENAI_API_KEY` — in Colab this is read via `google.colab.userdata`; locally, export it as an environment variable and adjust the key-loading cell accordingly.
- The `wk4`, `wk10`, `wk12`, `wk13` notebooks use the **MostlyAI** local SDK (`mostlyai[local]`) to train and sample synthetic data generators, which is compute-intensive and benefits from a GPU.
- `google-colab`-specific cells (`google.colab.userdata`, `google.colab.files`) only run inside Colab and will need to be swapped for local file I/O / env vars if running elsewhere.

## Reproducibility

Each major experiment writes a `wk*_manifest.json` to `results/`, capturing library versions, random seeds, and participant splits at the time of the run, so results can be traced back to the exact configuration that produced them (see e.g. [results/wk10_manifest.json](results/wk10_manifest.json)).

This provenance pattern was introduced starting with `wk10`. The `wk2`, `wk3`, and `wk4` notebooks call `.to_csv(...)` on their own results tables, but those files were written to the Colab runtime's local disk and were never downloaded or committed — they are not recoverable and do not exist in this repository. The numbers those notebooks report only exist as printed cell output inside the committed `.ipynb` files themselves.
